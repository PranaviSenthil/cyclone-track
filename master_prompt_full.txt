# PHASE 3 — REAL MODEL TRAINING AND SCIENTIFIC EVALUATION

## 3.1 Define the actual forecasting problem

The primary task is cyclone-track forecasting from observations available at the forecast issue time.

Predict future cyclone positions at 24, 48, and 72 hours. Add a 12-hour horizon only if the dataset and evaluation pipeline support it.

Inspect the existing track GRU and preprocessing code. Reuse the existing architecture where reasonable.

Do not assume the existing checkpoint is valid merely because it loads.

## 3.2 Build leakage-safe sequences

Implement or repair sequence preparation with these rules:

- Sort observations by storm ID and timestamp.
- Keep all sequences within their respective storm.
- Use only past information to form input windows.
- Do not use future track, wind, pressure, or final-track information as input.
- Fit scalers and preprocessing only on training storms.
- Apply the same fitted transformations to validation and test data.
- Handle missing observations explicitly.
- Detect irregular temporal gaps.
- Do not interpolate across large gaps without a documented rule.
- Preserve a distinction between observed and interpolated values.
- Record sequence counts and rejection reasons.
- Verify the input timestamps precede the forecast issue time and target timestamps follow it.

Do not assume every observation can be safely resampled to a 3-hour grid.

## 3.3 Establish baselines first

Implement at least:

1. Persistence baseline: future position equals the latest observed position.
2. Constant-motion baseline: extrapolate recent motion using only past positions and elapsed time.
3. A historical or climatological baseline only if it can be constructed without leakage and is scientifically defensible.

Evaluate baselines and trained models on exactly the same eligible test sequences.

Use correct geodesic distance calculations for track errors. Clearly document any approximation.

## 3.4 Train the track model

Use the verified training storm manifest only.

Requirements:

- Compact CPU-feasible model configuration.
- Reproducible seeds.
- Training-only preprocessing.
- Validation-based hyperparameter selection.
- Early stopping.
- Best-validation-checkpoint saving.
- Training and validation loss histories.
- NaN/Inf detection.
- Documented units and feature definitions.
- Model configuration and checkpoint hashes.

Save predictions separately from evaluation summaries.

Do not tune against the test set.

## 3.5 Evaluate track prediction honestly

Calculate genuine metrics at each forecast horizon:

- Mean geodesic track error in kilometres.
- Median geodesic error.
- 90th-percentile geodesic error.
- Number of evaluated sequences.
- Number of unique evaluated storms.
- Per-storm metrics.
- Results for AMPHAN and BIPARJOY where valid data supports the requested horizon.

Compare the model with each baseline on identical cases.

Report absolute error and relative improvement or degradation. If the neural network performs worse than a baseline, report it clearly.

Do not remove difficult storms or change metric definitions after inspecting the test results.

Audit the existing intensity model and its targets.
